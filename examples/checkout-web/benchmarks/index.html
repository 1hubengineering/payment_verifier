SDK 0.2.0 candidate · 19 November 2026

Verification benchmarks

How fast the SDK processed synthetic receipts and committed claims to SQLite on a shared VPS.

More parallel work raised throughput and tail latency

In two runs of 300 successful receipts, raising concurrency from one to four increased throughput from 131.6 to 322.6 attempts/s. The time within which 95% of attempts finished rose from 9.69 to 52.32 ms. Each setting was run once.

Successful receipts at concurrency 1 and 4

Both runs used 300 scenarios and one attempt per scenario. Concurrency is the maximum number of scenarios running at once.

What the other workloads tested

60 successful receipts
The shorter serial run measured 130.3 attempts/s. Use the two 300-scenario runs for the concurrency comparison.
Mixed outcomes
Fifty scenarios each covered a match, three kinds of mismatch, a missing receipt and a simulated network failure. Outcomes can finish through different code paths.
Recovery
300 scenarios generated 800 attempts because the workload injected timeouts, network failures and lost commit responses, then exercised recovery.
Claim contention
300 scenarios formed 150 pairs competing for the same receipt within each pair. Every pair produced one winning claim and one duplicate-claim rejection.

Every workload met its expected outcome assertions. Compare throughput and latency within the same workload and sample size. The mixed, recovery and contention runs exercise different code paths and do not rank success capacity.

Run data and metric definitions

Scenarios and attempts (counts)
Scenarios are test cases. Attempts count individual verification calls, including retries. These are sample sizes.
Throughput (attempts/s)
Attempts divided by measured elapsed time. Higher is better for equal work.
Latency (ms)
p50, p95 and p99 mark the times within which 50%, 95% and 99% of attempts finished. Lower means faster responses. These use nearest rank.
CPU (average cores)
Process CPU time divided by elapsed time. 1.00 means one core on average. Lower uses less CPU at equal throughput.
Peak resident memory (MiB)
The benchmark process’s memory high-water mark, including initialization. Lower uses less memory under equivalent conditions.

Test environment and Chromium probe

Source candidate f441981. Shared AMD EPYC VPS with four vCPUs and 7.75 GiB RAM. Ubuntu 26.04.1 LTS, Linux 7.0.0, Docker 29.1.3 and Compose 2.40.3. The backend container was limited to two vCPUs and 768 MiB. Node.js 26.13.1 and SQLite 3.54.1 used the direct SQL adapter with an ext4-backed Docker volume.

Each workload used ten warm-up scenarios, a 3 ms mock provider delay, and a 50 ms timeout budget. The measured interval excludes warm-up and expectation registration. Receipt HTML parsing and Chromium were outside the benchmark.

In a separate local probe, Chromium 159.0.8154.6 under Playwright 1.65.1 took about 1.20 seconds to launch and 0.36 seconds to render a small page. Container memory rose from about 136 MiB to 295 MiB while the browser was open. Live provider latency and production capacity were outside the test scope.
