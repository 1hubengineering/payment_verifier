# Payment Verifier 0.2.0 VPS validation

Date 19 November 2026 (Africa/Nairobi). This report concerns the 0.2.0 source
source snapshot and the private portal on the existing VPS. The initial Docker image was
built from clean commit `f4419813cc78a4d6b3b7c742100c269ea4b6bb28`. The public
Pages workflow deployed a separate commit containing the matching SDK runtime
source, static UI, and sanitized results.

## Environment and isolation

The VPS had four AMD EPYC vCPUs, 7.75 GiB RAM, and 58 GiB available on its ext4
root filesystem at audit. Ubuntu 26.04.1 LTS ran Linux 7.0.0-42-generic with
Docker Engine 29.1.3, Compose 2.40.3+ds1-0ubuntu1, and cgroup resource controls.
The existing Bingo edge owned ports 80 and 443. Its six containers were recorded
by identity, startup time and restart count for a later comparison.

AndHub has a separate Docker project, bridge network and named volumes. The
portal uses fresh SQLite via the direct adapter. The backend and Caddy are
capped at 2 vCPUs / 768 MiB and 0.5 vCPU / 128 MiB respectively. The backend
has 128 MiB of shared memory and at most one concurrent official verification.
Caddy publishes HTTPS to VPS loopback port 4443. Existing SSH access provides
the client tunnel.

## Operator access and recovery

Run the following on the local machine and keep the tunnel open.

```sh
ssh -NT -o ExitOnForwardFailure=yes -L 127.0.0.1:4443:127.0.0.1:4443 bingo-vps
```

Retrieve the portal's **public CA certificate** over the existing SSH connection.
Import it into the operator browser's trusted certificates and open
[https://localhost:4443](https://localhost:4443/). To check health with just that
CA, run the two commands below locally while the tunnel is open.

```sh
ssh bingo-vps '/opt/andhub-verifier/control/compose exec -T https cat /data/caddy/pki/authorities/local/root.crt' > andhub-portal-ca.crt
curl --fail --cacert andhub-portal-ca.crt https://localhost:4443/health
```

The account name is `admin`. From a local Bash terminal, reset it to a strong
initial password you generate in your password manager. The SSH command reads
the password from stdin. At sign-in, choose a different long password to unlock
**Live Verification** and **Benchmarking**. For a new empty store use `seed`
instead of `rotate`.

```bash
read -r -s -p 'Initial administrator password: ' portal_password
printf '\n'
printf '%s\n' "$portal_password" | ssh -T bingo-vps '/opt/andhub-verifier/control/compose exec -T playground ./node_modules/.bin/varlock run -- node src/server/admin.ts rotate admin'
unset portal_password
```

Use the same command to recover lost access. It revokes sessions and requires
another password change. Empty credentials and wrong-origin mutations are rejected.
If the account looks unavailable after repeated attempts, wait one minute.
If the browser cannot open the page, check the tunnel, local port conflicts and
the downloaded CA. Keep the local entry on port 4443 or configure the exact
browser origin at deployment. Remove the CA from your browser after retiring this
deployment.

## Deploy, back up, and roll back

Prepare the project from a reviewed commit. Transfer a Git archive into
`/opt/andhub-verifier/releases/<commit>` and point `current` to it. Set the
persistent Varlock/Compose inputs in `/opt/andhub-verifier/control/vps.env` with
0600 permissions. The deployed helper `control/compose` runs this wrapper. Make it executable and
keep the control directory private.

```sh
#!/bin/sh
set -eu
cd /opt/andhub-verifier/current/apps/verification-playground/deploy
if [ -f compose.telebirr.yaml ] && [ "${PLAYGROUND_USE_TELEBIRR_TUNNEL:-1}" = 1 ]; then
  set -- -f compose.telebirr.yaml "$@"
fi
exec docker compose --env-file /opt/andhub-verifier/control/vps.env \
  -p andhub-verifier -f compose.yaml -f compose.cbe.yaml -f compose.vps.yaml "$@"
```

Configure the reviewed commit and set
`PLAYGROUND_ORIGIN=https://localhost:4443`, `PLAYGROUND_SITE=localhost`, and
`PLAYGROUND_SECCOMP_PROFILE` to the generated profile path. Build the pinned
Chromium target, start the project, and verify health.

```sh
/opt/andhub-verifier/control/compose config --quiet
/opt/andhub-verifier/control/compose build playground
/opt/andhub-verifier/control/compose up -d --wait
/opt/andhub-verifier/control/compose ps
/opt/andhub-verifier/control/compose logs --tail 40 playground
```

Prepare the Chromium seccomp profile from Playwright's pinned upstream source
using the repository's digest-checking helper. Use the generated profile
with the unprivileged worker, dropped capabilities and active OS sandbox.

```sh
curl --fail --silent --show-error --location \
  https://raw.githubusercontent.com/microsoft/playwright/v1.65.1/utils/docker/seccomp_profile.json \
  -o playwright-1.65.1-seccomp.json
node apps/verification-playground/deploy/prepare-chromium-seccomp.mjs \
  playwright-1.65.1-seccomp.json chromium-seccomp.json
```

Before an update, stop the project from accepting work and back up its
`playground-data`, `https-data` and `https-config` volumes using consistent
offline snapshots. Protect those backups as private material. Retain the previous
commit directory, image and deployment settings. For a rollback, stop the project,
point `current` and `PLAYGROUND_SOURCE_ID` back to the matching commit and image,
restore the corresponding backups if the store format changed, and run
`control/compose up -d --wait`. For the first deployment, rolling back simply
stops the AndHub project. Keep claim history by preserving its volumes and backups.
Old snapshots can omit claims committed since the backup. Reconcile them before
reopening live verification. Avoid resetting active SDK stores.

## Deployment acceptance

- Trusted HTTPS returned HTTP 200 from the operator tunnel and again after the
  portal restart. The proxy's host listening socket was bound to VPS loopback.
  The Fastify service used the project network and exposed health to Compose.
- Anonymous history and benchmark calls returned HTTP 401. A cross-origin
  sign-in mutation returned HTTP 403. The browser verified Secure, HttpOnly,
  SameSite=Strict cookie attributes, the forced password change, a reload using
  the same session, and logout with a subsequent HTTP 401.
- Both official adapters were configured. Synthetic verification returned the
  expected amount tolerance decision and report. An original attempt replay
  returned the stored response, and malformed reuse of its portal attempt ID
  returned HTTP 409.
- The dashboard completed six controlled measurements and cancelled a 600-item
  recovery run. Restart retained one admin, eight benchmark history rows
  (including the UI smoke and cancelled run), and two synthetic verification
  history rows.
- The six Bingo containers matched the before snapshot by container ID, startup
  time, and restart count. No Bingo configuration or storage was changed.
- GitHub Pages served the documentation, synthetic playground, benchmark table
  and candidate page. Chromium completed the hosted CBE SMS scenario offline
  with no cross-origin requests.

## Authorized live smoke

On 19 November 2026, the operator supplied one receipt per provider for a live
smoke test. The deployed SDK and official adapters made one lookup per provider.
Each run used an in-memory SQLite store. The messages supplied the comparison
amounts and recipients. They lacked an independent order invoice, so the smoke
used a generated invoice reference and was limited to retrieval and extraction
validation. The first Telebirr attempt stopped locally with
`EXPECTATION_EXPIRED` before provider access. The smoke then used a test window
open at execution time for its single Telebirr lookup.

| Provider | SDK result                               | Stage               | Adapter time | Total verification |
| -------- | ---------------------------------------- | ------------------- | -----------: | -----------------: |
| CBE      | `UNAVAILABLE` / `RECEIPT_RENDER_TIMEOUT` | `receipt_rendering` |      15.17 s |            15.19 s |
| Telebirr | `UNAVAILABLE` / `PROVIDER_TIMEOUT`       | `receipt_retrieval` |      15.03 s |            15.14 s |

Both outcomes were retryable. Comparison checks were unavailable because
neither adapter produced parsed receipt evidence. Both identical replays
returned the committed outcome without another lookup, and malformed input
under the bound key returned `IDEMPOTENCY_CONFLICT`.

### Browser follow-up

The operator confirmed that both official receipt pages loaded after several
browser attempts over Ethio Telecom mobile data. The screenshots show completed
statuses for both providers. In subsequent browser tests, the operator reported
that CBE also loaded on other networks and through VPN exits in multiple
countries. The Telebirr page loaded only on Ethio Telecom among the tested
connections. These observations apply to the receipt and connections tested.
The [tunnel follow-up](#telebirr-workstation-tunnel) exercises the SDK over that
same connection from the VPS.

The Telebirr page separates the transferred amount from the total including
fees and uses the transaction number as its invoice number. It shows an
additional surname for the credited party compared with the SMS. If the SDK
extracts the full name, an expectation based on the shorter SMS name would fail
the existing recipient check, which normalizes spacing and case before
requiring the names to match. An order verification needs the trusted recipient
name and invoice reference from the host.

### Deployed fix for the current CBE page

The CBE receipt URL returns a client-rendered Nuxt shell. The receipt fields
come from CBE's separate JSON service. The legacy sandbox could load the shell
but had no receipt fields to read. This explains the missing heading in the
120-second run.

The adapter now recognizes that shell and requests the data directly from a
fixed CBE endpoint, using the original validated receipt identifier. Public
IPv4 validation, TLS, redirect rejection, and the shared byte and time budgets
apply to both HTTPS requests. The older inline layout still uses the sandboxed
browser. The SDK still requires all payment checks and a committed claim.

The deployed portal image is `c828328`. The HTTPS health check passed and the
Bingo container IDs, startup times, and restart counts matched the pre-deploy
check. The prior image, `f441981`, is retained for rollback. Full
`pnpm verify` passed for `c828328` on Node 26.13.1, including 338 workspace tests,
40 web tests, 297 adapter contract tests, 11 frozen reference tests, and
installed-package checks. Lint reported the four existing portal warnings.

One ordinary diagnostic request returned HTTP 200 and confirmed the shape of
the JSON fields. The staged adapter saw a timeout and a separate HTTP 401.
After deployment, the receipt page returned HTTP 200, and the CBE data request
returned HTTP 401 in about 3.6 seconds. A bounded follow-up confirmed that CBE
sent a `WWW-Authenticate: Bearer` challenge. The SDK returned
`UNAVAILABLE / PROVIDER_HTTP_ERROR` in about 3.7 seconds and performed no
payment checks. This was the outcome of the direct-client deployment. The
browser fix below supersedes that deployment.

### Proof-of-concept comparison and browser fix

The mounted Windows proof of concept matched the frozen reference. It navigates
Chromium to the receipt URL and allows CBE's page to load its data. Live
comparison used a fresh browser with scoped CBE traffic, with third-party
requests blocked. The data GET returned HTTP 200 on the workstation and the VPS.
The successful requests used the official receipt page origin and contained no
cookies or authorization header. From the same workstation, the previous
direct SDK client received HTTP 401.

The revised adapter uses the genuine browser request against the fixed CBE
data URL from the fetched receipt page's origin. The page's scripts and assets
stay blocked. It permits only the data GET and its CORS preflight and pins
the data host to validated public IPv4. The request omits credentials, verifies
TLS, and rejects redirects. The browser decodes the CBE JSON response under
the shared byte and time budget. The older inline receipt path stays offline.
The updated adapter extracted the authorized receipt's amount, recipient
account suffix, timestamp and reference on the workstation in 2.37 seconds.

The VPS deployed commit `319aa15` and the portal passed its HTTPS health
check. The Bingo container IDs, startup times, and restart counts matched the
previous audit. The prior portal image remains available for rollback.

The live VPS SDK test retrieved and compared the authorized CBE receipt in
4.16 seconds. Provider, bank transaction ID, completed status, amount,
currency, recipient name, account suffix, date and transfer type all passed.
The test supplied a generated order reference on purpose, so comparison
returned `INVOICE_REFERENCE_MISMATCH` and created no claim. An identical
repeat returned the same result with one adapter call in total.

`pnpm verify` passed from clean commit `319aa15` in a disposable Docker test
network. It covered 339 workspace tests, 40 checkout tests, 297 storage adapter
contract cases, 11 frozen reference tests, installed packages, and the website
and documentation builds. Lint reported five warnings and zero errors. The
follow-up test fixture cleanup removed the new warning, and all three browser
transport tests passed again.

### Telebirr workstation tunnel

The portal can route Telebirr receipt lookups through a workstation on Ethio
telecom. The workstation starts a reverse SSH forward to the fixed official
receipt host, using the existing VPS login. The portal reaches it through a
private Unix socket and checks Telebirr's HTTPS certificate. The VPS opens no
TCP proxy port, and CBE continues to use its existing adapter.

Use the [workstation connection instructions](../../apps/verification-playground/README.md#telebirr-over-ethio-telecom)
from WSL while connected to Ethio telecom. The VPS `control/vps.env` sets
`PLAYGROUND_TELEBIRR_TUNNEL_DIR=/opt/andhub-verifier/telebirr-tunnel`. The
directory is private under the AndHub deployment directory. The SSH script
sets mode `0660` on the socket for the playground's group. If the socket is
missing or stale, the portal reports the retryable `TELEBIRR_TUNNEL_OFFLINE`
diagnostic. After reconnecting, select **Run again**.

To switch the portal back to direct retrieval, stop the workstation tunnel and
recreate only the playground. Keep the same image and data volume.

```sh
PLAYGROUND_USE_TELEBIRR_TUNNEL=0 /opt/andhub-verifier/control/compose \
  up -d --wait --no-deps --force-recreate playground
```

The first tunnel run retrieved the authorized receipt in 2.35 seconds. The SDK
rejected the table layout. An in-memory comparison reproduced nested tables,
omitted tags, a stray cell attribute quote, and summary rows that the parser
mistook for invoice rows. The revised parser extracted the transaction number,
completed status, transferred amount, recipient, account suffix and payment
time in an in-memory check. The receipt contained the Telebirr transaction
number and lacked the separate merchant order reference required for a claim.

The final VPS build `2d49b60` read and compared the receipt in 3.52 seconds.
Provider, transaction number, amount, currency, completed status, recipient,
account suffix and payment time passed. The independent order reference was
missing, so the SDK returned `REQUIRED_FIELD_MISSING` at `comparison` and
created no claim. An identical replay used the committed result with one
provider lookup in total. The smoke test used a disposable in-memory store.

Stopping the tunnel left a stale socket and produced the expected retryable
unavailable result. Reconnecting replaced the stale socket. A synthetic TLS
server with a trusted certificate for a different hostname was rejected. The
portal passed its HTTPS health check and Bingo's container identities, start
times and restart counts matched the preflight snapshot. The previous portal
image and deployment environment remain available for rollback.

`pnpm verify` passed from clean commit `2d49b60` on Node 26.13.1. The run
included 348 workspace tests, 40 checkout tests, 297 adapter contract cases,
11 frozen reference tests, installed packages, site builds and the docs smoke
check. Lint reported five existing warnings and zero errors.

## Release validation

The source deploy used the candidate build and private workspace application
packages. The [hosted library workflow](https://github.com/1hubengineering/payment_verifier/actions/runs/44564436492)
passed on Node 24.22.3 and 26.13.1 for the public SDK source commit. The private
VPS snapshot includes the portal and benchmark packages in addition to the
matching verifier runtime source.

`pnpm verify` passed from the clean private commit on Node 26.13.1 in a disposable
Docker test network. It passed 325 workspace tests, 40 web tests, all 297 cases
on the nine direct SQL / Drizzle / Prisma engine combinations, and 11 frozen
reference cases. The same command checked types, builds, Drizzle Kit operations,
installed package archives, and docs MCP. The installed checks exercised the
browser-safe comparison dependency graph. Lint reported four warnings for
closure-based auth handlers passed directly to Fastify and an extra header
object spread, with zero errors.

The SDK tests demonstrated committed-key conflict on malformed evidence,
original-evidence replay without a provider request, and typed
`RECEIPT_BROWSER_UNAVAILABLE` at `receipt_rendering` with renewed admission
after failed launches. The CBE tests used the actual sandbox and synthetic
documents and transport.

The npm registry reports all five SDK packages at 0.2.0. Package metadata lists
the core publication at 18:45 EAT on 19 November 2026. This deployment performed
no release approval, package publication or tagging. The npm core has the
`/input` export and the deployed workspace adds `/comparison`. A fresh registry tarball passed a synthetic input and comparison smoke. The
GitHub release list had no `v0.2.0` entry at review.

The next live gates are CBE and Telebirr order checks using trusted merchant
references present on the official receipts. Keep active 0.1.1 stores on their
existing versions until a cutover demonstrates that claims survive.
