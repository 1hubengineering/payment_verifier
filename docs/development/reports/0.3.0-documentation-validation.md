# Payment Verifier 0.3.0 documentation validation

## Release and scope

On 20 November 2026 (Africa/Nairobi), npm reported `latest: 0.3.0` for
`verifier`, `storage-sql`, `adapter-drizzle`, `adapter-prisma` and `provider-cbe`
in the `@1hubengineering` scope. The five downloaded npm tarballs matched the
SHA-256 values published in the GitHub release. Its tag resolves to
`8213fff63f1f9afae8cb5b3198492e0985f71831`.
[Publication evidence](../releases/0.3.0.md) ·
[Release checksums](https://github.com/1hubengineering/payment_verifier/releases/download/v0.3.0/SHA256SUMS)

The README, versioned guide, runnable examples and published API reference
target npm 0.3.0. The local Pages build extracts declarations from those
checksum-verified archives. The 0.1.0–0.2.0 guide bodies retain their own release
baselines. The workspace guide and private examples describe repository code.
The deployment page identifies the post-release CLI diagnostic and its
published SDK equivalents. The VPS report describes its historical snapshot.

## Commands and observed results

- `npm view @1hubengineering/<package> dist-tags --json` returned 0.3.0 as
  latest for each package. `npm pack --json` and `sha256sum *.tgz` matched
  every row of the GitHub release checksums.
- In fresh consumers, install the pinned packages from [checkout](../../0.3.0/checkout.md)
  and run `node compare-receipt.mjs`, `node persistent-checkout.mjs "$(mktemp -d)"`
  and `node check-custom-storage.mjs "$(mktemp -d)"`. These checked the offline
  result, a synthetic provider timeout, key recovery, mismatch, invalid input,
  duplicate rejection, repeat-safe host writes and adapter locking/rollback.
  All three commands passed on Node 24.22.3 and 26.13.1.
- `pnpm db:up` brought up the disposable PostgreSQL and MySQL services.
  `pnpm verify` passed on Node 26.13.1. This included 363 workspace tests,
  40 checkout web tests, 297 real-engine contract tests (nine cells × 33) and
  11 frozen reference tests. It also passed environment and schema generation,
  packaging, installed-consumer checks, type checks, site build and MCP
  smoke. Existing lint warnings and bundler directive warnings were nonfatal.
- `pnpm check:deployment --provider telebirr` and
  `pnpm check:deployment --provider cbe` exited 0 with network explicitly
  skipped. The CBE command passed the sandboxed browser check. Neither
  reported readiness for a live smoke test.
- The link check walked generated HTML anchors, repository-relative Markdown
  links, and GitHub source links against local or tagged repository paths.
  A local Chromium run exercised keyboard skip navigation, question links,
  an idempotency deep link, a published API declaration and page width.
- The [pull request checks](https://github.com/1hubengineering/payment_verifier/actions/runs/44739653409)
  passed on Node 24.22.3 and 26.13.1. The
  [Pages workflow](https://github.com/1hubengineering/payment_verifier/actions/runs/44740204396)
  built, tested and deployed the static site from commit `ce432f3aabe6`.
- Public HTTP checks returned 200 on all seven routes. The persistent example
  was downloadable from the merged branch. A mobile Chromium browser
  followed the checkout, common questions and idempotency links and found
  the published `VerificationOperationError` declaration through API search.

## Independent newcomer exercise

A fresh agent received the proposed public README, versioned guides, and
synthetic examples in an isolated copy. It installed the published packages
with npm and ran the documented commands. It then created a loopback Node HTTP
checkout with two SQLite stores. Its test runner started three server
processes using those same stores. Unauthorized customers were rejected before
the fixture ran. The checkout left orders pending after a timeout and replayed
the first observation without retrieval. It deliberately lost the response to
a fresh successful observation after the SDK commit, then recovered it in two
concurrent requests after restart. Both yielded the same verification ID,
zero fresh retrievals and one download grant. An authorized buyer in a
different tenant could not reuse the claimed provider transaction.

The exercise ran the independent HTTP runner with
`node checkout-variant/exercise-download-checkout.mjs <fresh-directory>`.
It found that the original docs left the timing of saving the original
submission pair implicit, and that npm saved caret ranges even with an exact
version on the command line. The guides now show preserving the pair or a
secure reference before the first request and use `npm install --save-exact`.
The curated snapshot omitted some companion files. Repository link checks
confirmed those paths.

The agent retested the two revised install commands in fresh consumers and
confirmed literal versions in both manifests and lockfiles. It ran the
documented examples and independently repeated the recovery twice. Before
the first request, a separate client saved the key and canonical locator.
After the lost response it exited. A fresh client and backend then replayed
twice concurrently from the saved request. Both runs returned the original
verification with zero new lookups and one download grant.

## Provider connectivity preflight

On 20 November 2026 (Africa/Nairobi), the published npm 0.3.0 core and
CBE adapter ran in a temporary directory inside the existing private verifier
container, as its service user on Node 26.13.1. The running portal stayed on its
historical 0.2.0 snapshot. The diagnostic used `checkProviderConnectivity`
with an eight-second deadline and `checkCbeBrowser` with its offline fixture.
The run sent TLS handshakes and no receipt requests.

| Check                      | Result                                                              |
| -------------------------- | ------------------------------------------------------------------- |
| CBE direct TLS             | Both official receipt and data hosts passed certificate validation. |
| CBE browser                | The sandboxed Chromium test passed.                                 |
| Telebirr direct TLS        | `PROVIDER_TIMEOUT`. The diagnostic did not identify the cause.      |
| Telebirr configured tunnel | `PROVIDER_NETWORK_ERROR` with `TELEBIRR_TUNNEL_OFFLINE`.            |

Full receipt validation needs an approved locator and an independent
merchant-owned order snapshot for each provider. Telebirr also needs a
working provider route from the verification runtime.
